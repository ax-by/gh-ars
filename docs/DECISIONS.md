| slice CPUQuota 를 정수 퍼센트가 아닌 문자열로 넘기고, cpu 하한을 R25 검증 오류로 둔다 [§9.3, R25] | DESIGN §3.4(`SystemdProps` → `"200%"`)와 §4.3(`Create(..., cpuQuotaPercent int, ...)`)은 정수가 아닌 cpu 에서 양립하지 않았다. int 를 경유하면 `cpu: 0.125` 가 `12%` 로 잘려 none 모드(`--cpus=0.125`)와 sidecar 모드의 예산이 달라지고 §8.1 의 "unit 예산 하나" 전제가 깨진다. 하한 아래 값을 조용히 클램프하는 대신 시작 시 오류로 떨어뜨려 규범을 SPEC 에 남긴다 | 정수 퍼센트 + 1% 클램프(적용값이 사용자 값과 달라짐, 근거가 SPEC 밖에 남음) |
| R19 의 키 파일 암호화 판정을 PEM 머리 파싱으로 한다(openssh-key-v1 의 ciphername/kdfname, `Proc-Type: 4,ENCRYPTED`, `ENCRYPTED PRIVATE KEY`) [R19] | R19 는 정적 규칙이라 config 가 판정한다(§7.1-1). `golang.org/x/crypto/ssh` 는 Phase 8 도입(DESIGN §10)이고, 판정 조건은 `ssh.ParseRawPrivateKey` 가 `PassphraseMissingError` 를 내는 조건과 같아 결과가 달라지지 않는다 | x/crypto 를 Phase 2 로 앞당김(쓰지 않는 SSH 코드가 먼저 들어옴) / R19 를 executor/ssh 로 미룸(§7.1-1 의 정적 규칙 목록과 충돌) |
| spread의 사용률 분자를 `running`이 아니라 `occupied`로 둔다 [§8.2, §8.3] | Dying(부품 잔존)·Foreign unit은 머신 리소스를 실제로 잡고 있다. 여유 슬롯만 occupied로 세고 사용률은 running으로 세면, 정리에 실패한 머신이 사용률 0으로 보여 새 unit이 몰린다(§8.3이 slot 점유를 유지하는 이유와 정면으로 충돌). 배치 판단에 쓰는 두 값의 기준을 하나로 맞춘다 | 사용률은 running, 여유 슬롯은 occupied (Spread에 두 map을 넘김) |
| `Executor.Run`의 비0 종료는 오류가 아니라 `Result.ExitCode` [DESIGN §4.1] | 종료 코드로 분기하는 호출자가 있다: preflight의 podman 경로 고정(§10.2 규칙 3)은 `podman info` 실패를 보고 `sudo -n podman info`로 넘어가고, 정리 단계(§8.3)는 "이미 없음"을 성공으로 본다. 오류를 받아야 하는 실패(바이너리 없음, 접속 끊김, 취소)와 명령의 정상적인 부정 응답이 섞이지 않는다. SPEC은 이 수준을 정하지 않아 DESIGN §4.1에 명시했다 | 비0을 오류로 반환(호출자가 매번 `exec.ExitError`를 풀어야 하고, ssh 구현에서는 그 타입이 달라져 분기가 갈라진다) |
| 파이프 대기에 상한(`WaitDelay`)을 두고, 상한이 발동하면 종료 코드 0도 오류로 돌려준다 [DESIGN §4.1, §7.2-4] | 파이프는 자식의 fd를 물려받은 손자가 사는 동안 열려 있다. `sudo -n podman info`처럼 손자가 남으면 `Run`과 스트림의 `Read`·`Close`가 그 수명만큼 반환하지 않아, 기동 타임아웃 2분이 지나도 `startUnit` goroutine이 풀리지 않고 events 재시작도 영영 일어나지 않는다(둘 다 테스트로 재현했다). 상한이 실제로 걸리게 하려고 두 가지를 `exec`에서 가져왔다: 스트림 stdout은 `StdoutPipe` 대신 `io.Pipe`를 써서 `Wait`이 `Read`와 나란히 돌게 하고(`StdoutPipe`는 "다 읽은 뒤 `Wait`" 순서를 요구하는데 EOF가 오지 않으면 `Wait`이 시작되지 못한다), stdin은 `*os.File`을 넘겨 `exec`가 복사 goroutine을 만들지 않게 한다(그 goroutine이 `Read`에 막히면 `WaitDelay`로도 풀리지 않아 상한이 stdin 경로에서만 무효가 된다). 대신 호출자는 즉시 반환하는 Reader를 준다 — §7.2-4의 tar 스트림은 메모리에서 만든다. 상한이 가려지는 예외가 하나 남는다: 자식이 비0으로 끝나면 `os/exec`가 `ExitError`를 우선해 드레인 만료를 덮는다. 비0 응답에서 stdout을 신뢰하는 호출자가 없어 허용하고 DESIGN §4.1에 적었다. 이 상한은 취소뿐 아니라 자식의 정상 종료에서도 시작하므로(`os/exec`의 `WaitDelay` 계약) 발동 시 출력이 잘렸을 수 있다 — `docker ps` 결과가 조용히 잘리면 §8.3 판정이 틀어지므로 성공 값으로 돌려주지 않는다 | 프로세스 그룹째 kill(플랫폼별 분기가 생기고, sudo가 만든 프로세스 그룹에는 권한이 필요하다) / 상한 없음(goroutine 누수) / 상한을 취소 경로에만 거는 별도 구현(`os/exec`가 값 하나로만 노출해 파이프를 직접 관리해야 하고, 취소 시 stderr를 잃는다) |
| 재동기화(`msgResynced`)는 known unit의 `Parts`만 스냅샷으로 덮어쓰고 `State`·`Busy`는 유지한다 [§8.3, DESIGN §5·§6] | Parts는 머신 관찰로만 확정되는 사실이라 캐시가 어긋나면 §8.3의 slot 점유 계산이 틀어진다.
